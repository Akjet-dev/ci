# Ветки и деплой

Kubernetes-конвейер добавляется **рядом** с действующим деплоем на сервер и не пересекается с ним ни
одним триггером. Действующие workflow не меняются, не переименовываются и не отключаются.

## Модель веток

| Ветка | Куда деплоит | Что происходит при push |
|---|---|---|
| `main` | действующий production (сервер) | существующий `deploy.yml`, без изменений |
| `dev/v1`, `dev/v2`, `dev/clockster` и другие `dev/*` | действующий stage (сервер) | существующий `deploy.yml`, без изменений; Kubernetes-workflow **не запускаются** |
| `dev-k8s/release` | Kubernetes DEV | проверка values → сборка → сканирование → публикация → деплой в `dev-<сервис>` (когда включён) |
| `stage-k8s/release` | Kubernetes STAGE | проверка values STAGE → сборка → сканирование → публикация. **Деплоя из репозитория сервиса нет** |
| любая другая `dev-k8s/*` | никуда | проверка values DEV, сборка и сканирование без публикации |
| любая другая `stage-k8s/*` | никуда | то же, с values STAGE |
| любая другая | как сейчас | Kubernetes-workflow не запускаются |

Префикс `dev/` для Kubernetes не используется вовсе: в репозиториях уже есть ветки `dev/*`
(`dev/v1`, `dev/v2`, `dev/clockster`), и они не должны запускать Kubernetes-конвейер. Kubernetes-ветки
начинаются с `dev-k8s/` или `stage-k8s/`. Публикация образа привязана к **точным** именам
`dev-k8s/release` и `stage-k8s/release`, деплой в DEV — только к `dev-k8s/release`.

## Файлы в репозитории сервиса

| Файл | Назначение | Триггер |
|---|---|---|
| `deploy.yml` (существующий) | деплой на сервер | как сейчас; **не изменяется** |
| `k8s-build.yml` (новый) | проверка, образ, деплой в DEV | push в `dev-k8s/**`, `stage-k8s/**` |
| `k8s-deploy.yml` (новый) | деплой digest в DEV: повторный, откат, перезапуск, миграции | `workflow_dispatch` / `workflow_call`, только с ветки `dev-k8s/release` |

Шаблоны обоих новых файлов — в `examples/service-repo/.github/workflows/`. Ручной запуск
(`workflow_dispatch`) GitHub предлагает только для файла, который уже есть в ветке по умолчанию.

## Почему деплой не может уйти не туда

Проверки стоят в общем workflow, а не только в файлах сервиса:

| Что | Где закреплено |
|---|---|
| Деплой в DEV — только с ветки `dev-k8s/release`, только по событию push или ручному запуску | `deploy-k8s.yml`, шаг проверки цели и условие job'а деплоя |
| `stage` — только проверка манифестов; деплой из этого workflow невозможен | там же |
| Других окружений workflow не знает | там же |
| Неймспейс и релиз — только из values сервиса (`deployment.*`), без значения по умолчанию; метка раннера закреплена (`akjet-ds-apps`) | там же, шаг «Resolve the deployment from values» |
| Релиз приложения не создаёт маршрутов: HTTPRoute в рендере отклоняется | там же, шаг проверки манифестов |
| Образ публикуется только с `dev-k8s/release` и `stage-k8s/release` | `build-image.yml`, список `PUBLISH_BRANCHES` |
| Деплой выключен, пока переменная репозитория `K8S_DEV_DEPLOY_ENABLED` не равна `true` | `deploy-k8s.yml` и шаблон `k8s-build.yml` |

Это защита от ошибки и от случайного запуска. Она не заменяет прав в кластере: участник с правом
записи может написать собственный workflow в обход общего. Общий раннер приложений `akjet-ds-apps`
на тарифе GitHub Free находится в группе Default организации и доступен любому её репозиторию.
Поэтому фактическая граница — RBAC кластера: ServiceAccount раннера (`arc-runners/app-deployer`)
имеет только namespaced Role в DEV-неймспейсах приложений, для которых включены workload'ы; раннеров
и учётных данных STAGE в репозиториях сервисов нет вовсе (см. `docs/workflows.md`).

## Включение деплоя в DEV

До готовности платформы конвейер работает до публикации образа и на этом останавливается. Деплой
включается отдельным решением, когда для сервиса готовы: неймспейс, квота и сетевая политика; права
общего раннера в этом неймспейсе; маршрут (если нужен) в платформенном репозитории; pull-секрет
реестра; Secret'ы приложения; опубликованный чарт. После этого администратор репозитория создаёт
переменную `K8S_DEV_DEPLOY_ENABLED` со значением `true`.

## STAGE

Push в `stage-k8s/release` собирает и публикует образ и проверяет values STAGE, но ничего не
выкатывает. Выкатку в STAGE выполняет диспетчер в платформенном репозитории: его запускает участник
платформенной команды, указывая сервис, digest и коммит с values. Диспетчер принимает только digest,
который сейчас работает в DEV-неймспейсе сервиса. Функции GitHub Environments для этого не нужны.

Диспетчер и раннер STAGE в этой версии **не реализованы**; пока платформа держит STAGE выключенным,
ветка `stage-k8s/release` даёт только проверку и образ.

## Как изменение идёт от DEV к STAGE

1. Работа ведётся в `dev-k8s/<задача>`, затем вливается в `dev-k8s/release`.
2. Push в `dev-k8s/release` собирает образ и выкатывает его в DEV. Digest печатается в summary.
3. После проверки в DEV `dev-k8s/release` вливается в `stage-k8s/release`.
4. В STAGE выкатывается **тот же digest**, что проверен в DEV: образ повторно не собирается для
   выкатки. Сборка на `stage-k8s/release` служит проверкой ветки; её digest совпадает с DEV только
   если сборка воспроизводима, поэтому источником истины для продвижения остаётся digest из DEV.
5. Values STAGE берутся из `deploy/values-stage.yaml` на коммите ветки `stage-k8s/release`.

Один образ пригоден для обоих окружений, только если конфигурация не запечена при сборке.

## Сосуществование с действующим деплоем

- Ветки `dev-k8s/release` и `stage-k8s/release` создаются от `main` и регулярно получают из него
  изменения.
- Dockerfile, `deploy/` и `k8s-*.yml` можно держать и в `main`: workflow с триггерами только на
  Kubernetes-ветки при push в `main` не запускаются, а существующий `deploy.yml` их не использует.
- В существующий `deploy.yml` нельзя добавлять ветки `dev-k8s/**` и `stage-k8s/**`: в части
  репозиториев он выбирает путь на сервере по принципу «не `main` — значит stage».
- `tests/check_branch_model.py <каталог workflow> [--legacy-branch dev/v2 ...]` проверяет репозиторий
  сервиса на соответствие этой модели: существующие ветки запускают только существующие workflow,
  Kubernetes-ветки — только новые; старые имена (`dev/k8s`, `dev/*`) Kubernetes-workflow не запускают.

## Дальнейшая миграция

| Этап | Что меняется | Условие |
|---|---|---|
| 1. Сейчас | добавляются `dev-k8s/release`, `stage-k8s/release` и два workflow; действующий деплой не затронут | — |
| 2. DEV в Kubernetes | включается `K8S_DEV_DEPLOY_ENABLED` по сервисам | платформа готова, решение по каждому сервису |
| 3. STAGE в Kubernetes | диспетчер; выкатка проверенных digest | отдельное решение по STAGE |
| 4. Отказ от `dev/v1` | из существующего `deploy.yml` убирается ветка `dev/v1`; ветка архивируется | STAGE в Kubernetes заменил серверный stage для этого сервиса; имена хостов stage переключены |
| 5. Production | отдельный согласованный cutover. До него `main` деплоит на сервер, как сейчас | отдельное решение |
| 6. После cutover | `main` становится источником production-релизов в Kubernetes; серверный `deploy.yml` удаляется последним | production в Kubernetes принят |

Долгоживущие Kubernetes-ветки — две (`dev-k8s/release`, `stage-k8s/release`), плюс `main`; остальные
ветки `dev-k8s/*` и `stage-k8s/*` короткие и ничего не публикуют.
