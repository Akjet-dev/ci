# Reusable workflow для Kubernetes

| Файл | Где выполняется | Назначение |
|---|---|---|
| `.github/workflows/build-image.yml` | GitHub-hosted | сборка образа, публикация в GHCR, выдача digest |
| `.github/workflows/deploy-k8s.yml` | проверка — GitHub-hosted; деплой — раннер внутри кластера | `helm upgrade --install` общего чарта |
| `.github/workflows/chart-ci.yml` | GitHub-hosted | тесты этого репозитория; публикация чарта по тегу |

`deploy.yml` и `netbird/` — прежний деплой на сервер; они не менялись и с Kubernetes не связаны.

## `build-image.yml`

| Вход | По умолчанию | Смысл |
|---|---|---|
| `image` | имя репозитория | имя образа в `ghcr.io/<владелец>/` |
| `context` | `.` | контекст сборки |
| `dockerfile` | `Dockerfile` | путь к Dockerfile |
| `target` | — | стадия сборки |
| `build-args` | — | несекретные аргументы, по одному `ИМЯ=значение` в строке |
| `platform` | `linux/amd64` | поддерживается только это значение |
| `cache` | `true` | кэш слоёв в реестре, тег `buildcache` |
| `push` | `true` | публиковать образ; вне публикующих веток игнорируется |
| `scan` | `true` | сканировать образ на уязвимости и запечённые секреты |
| `scan-fail-on` | `CRITICAL` | уровни, к которым применяется проверка: секреты в образе этих уровней останавливают сборку всегда, уязвимости с исправлением — только в строгом режиме |

Секрет `build-secrets` (необязательный): строки `ID=значение`, которые вызывающий составляет из
собственных секретов. Внутри сборки они доступны только как секреты BuildKit
(`RUN --mount=type=secret,id=ID`) и не попадают ни в слои, ни в историю образа, ни в лог.
Значение секрета должно быть однострочным.

Выходы: `image` (`ghcr.io/<владелец>/<имя>`), `digest` (`sha256:…`, пусто, если образ не опубликован) и `published`.

Образ публикуется только с веток `dev-k8s/release` и `stage-k8s/release` (список закреплён в workflow). С любой другой ветки он собирается и сканируется, но в реестр не попадает. Порядок: сборка → сканирование → публикация; образ, не прошедший сканирование, не публикуется.

Вызывающему job'у нужны права `contents: read` и `packages: write`.

### Сканирование и режим проверки уязвимостей

Trivy сканирует каждый образ до публикации: все уязвимости HIGH и CRITICAL (в том числе без исправления) и секреты, запечённые в образ. Отчёт печатается в журнал, счётчики — в summary, JSON-отчёт сохраняется артефактом `trivy-report-…` на 14 дней.

| Что нашлось | `TRIVY_BLOCK_ON_CVES: 'false'` (сейчас) | `'true'` |
|---|---|---|
| Уязвимости с исправлением, уровень из `scan-fail-on` | предупреждение, образ публикуется | ошибка, образ не публикуется |
| Секреты в образе, уровень из `scan-fail-on` | ошибка | ошибка |
| Сканер не отработал или отчёт не читается | ошибка | ошибка |

Режим «только предупреждение» включён временно, на период миграции в Kubernetes. Вернуть блокировку — одна строка в `build-image.yml`: `TRIVY_BLOCK_ON_CVES: 'true'`.

### Работа с digest

Образ публикуется с тегом `sha-<коммит>`, но тег служит только для поиска. Деплой принимает
исключительно digest: он однозначно определяет содержимое и не может быть переписан. Digest
печатается в summary сборки и возвращается выходом `digest`.

## `deploy-k8s.yml`

| Вход | По умолчанию | Смысл |
|---|---|---|
| `environment` | обязателен | `dev`; `stage` — только вместе с `validate-only` |
| `validate-only` | `false` | проверить манифесты и не деплоить |
| `image-digest` | — | `sha256:<64 hex>`; обязателен для деплоя |
| `chart-version` | обязателен | точная версия общего чарта |
| `release` | имя репозитория | имя релиза Helm |
| `values-dir` | `deploy` | каталог с `values.yaml` и `values-<environment>.yaml` |
| `chart` | `oci://ghcr.io/<владелец>/charts/akjet-app` | либо `./путь` к чарту в репозитории сервиса |
| `run-migrations` | `false` | запустить Job миграций до обновления |
| `restart` | `false` | перезапустить pod'ы (после изменения Secret) |
| `timeout` | `10m` | таймаут `helm upgrade --wait`, если в values нет `deployment.rolloutTimeoutSeconds`; на ожидание миграции не влияет |
| `pod-logs-on-failure` | `false` | печатать хвост логов pod'ов при сбое |

Секретов workflow не принимает.

Чарт — приватный пакет GHCR. Оба job'а входят в реестр токеном запуска (`github.token`, передаётся через stdin) и сразу после загрузки выходят; персональные токены не используются. Для этого нужно:

- у вызывающего job'а — `permissions: contents: read` и `packages: read` (вызываемый workflow не может получить больше, чем дал вызывающий; без этого запуск останавливается на старте);
- у пакета чарта — доступ Actions на чтение для репозитория сервиса (настройки пакета → Manage Actions access).

### Куда идёт деплой

Куда и что деплоить, определяют values-файлы сервиса (раздел «Контракт values»); workflow сервисов не знает.
Раннер — общий для всех сервисов (`RUNNER_LABEL: akjet-ds-apps`): он выбирается до запуска job'а и поэтому
закреплён в workflow, а не взят из values.

Деплой выполняется, только если одновременно: окружение `dev`; запуск с ветки `dev-k8s/release`; событие —
push или ручной запуск; не задан `validate-only`; переменная репозитория `K8S_DEV_DEPLOY_ENABLED`
равна `true`. Для `stage` доступна только проверка манифестов. Подробнее — [ветки и деплой](branches.md). Это защита от ошибки, а не от злоумышленника: фактическую границу задают права
ServiceAccount'а раннера в кластере (см. ниже).

### Необязательные переопределения переменными репозитория

Источник конфигурации — values-файлы сервиса. Отдельные **несекретные** значения можно переопределить
переменной репозитория GitHub, если сервис явно разрешил это в `<values-dir>/overrides.yaml`:

```yaml
overrides:
  DB_HOST: { path: config.DB_HOST, type: host }
  APP_URL: { path: config.APP_URL, type: url }
```

| | |
|---|---|
| Имя переменной | `<ОКРУЖЕНИЕ>_<ИМЯ>`: `DEV_DB_HOST`, `STAGE_DB_HOST` |
| Порядок | `values.yaml` → `values-<env>.yaml` → переменные |
| Нет переменной или она пустая | действует значение из values-файла |
| Что можно переопределять | только `config.<ИМЯ>`; образ, релиз, неймспейс, раннер, реплики, securityContext и ссылки на Secret'ы — нельзя |
| Секреты | имена, похожие на учётные данные, отклоняются |
| Типы | `string` (по умолчанию), `host`, `url`, `integer`, `boolean`; значение проверяется и попадает в ConfigMap строкой |
| Переменная этого окружения, которой нет в списке | ошибка |
| Сервис без `overrides.yaml` | механизм не действует |

Переменные читаются как данные и в команды не подставляются. Набор переопределений вычисляется один раз, в
job'е проверки, и тот же набор применяется при деплое.

### Контракт values

Сервис описывает свой деплой сам, в `<values-dir>/values.yaml` (общее) и `values-<окружение>.yaml`. Порядок —
как у Helm: файл окружения перекрывает общий, словари сливаются, списки заменяются.

```yaml
# values.yaml
deployment:
  release: backend          # имя релиза Helm; объекты и Secret'ы называются <release>-…
  envBundle:
    secret: app             # необязательно: env-bundle целиком уходит в Secret <release>-app
image:
  repository: ghcr.io/akjet-dev/backend   # и сборка, и деплой; digest приходит из сборки того же запуска
requiredSecrets: { app: [APP_KEY] }       # Secret'ы, которые читают pod'ы
components: { web: { ports: { http: 8080 }, … } }
migration: { enabled: true, command: [...] }   # необязательная миграция

# values-dev.yaml
deployment:
  namespace: dev-lk-backend # неймспейс DEV; values-stage.yaml называет свой
```

| Поле | Обязательно | Правила |
|---|---|---|
| `deployment.namespace` | да | имя неймспейса Kubernetes, начинается с `<окружение>-` (DEV не может указать неймспейс STAGE и наоборот) |
| `deployment.release` | да | `^[a-z0-9]([a-z0-9-]*[a-z0-9])?$`, не длиннее 40 символов |
| `deployment.envBundle.secret` | нет | имя из `requiredSecrets`; включает сквозной режим `env-bundle` |
| `deployment.migrationWaitTimeoutSeconds` | нет | целое 60–5400: сколько секунд следить за Job миграций (скачивание образа входит). По умолчанию `migration.activeDeadlineSeconds` + 120 |
| `deployment.rolloutTimeoutSeconds` | нет | целое 60–3600: таймаут `helm upgrade --wait`. По умолчанию — input `timeout` |
| `image.repository` | да | образ под `ghcr.io/<владелец>/`, без тега и digest |

Других ключей в `deployment` нет: опечатка останавливает запуск. Блок `deployment` workflow читает сам и
перед передачей в Helm убирает (чарт 0.1.0 его не знает), поэтому `helm template` по этим файлам вручную
требует того же: `yq 'del(.deployment)' values.yaml`.

Неймспейс берётся **только** из values: без значения по умолчанию, без вывода из имени репозитория, без
неймспейса раннера или контекста kubeconfig. Нет значения или оно неверное — job проверки останавливается до
обращения к кластеру. Job деплоя читает values того же коммита ещё раз и останавливается при расхождении.
Каждая команда `helm` и `kubectl` получает этот неймспейс явно; Job миграций дополнительно получает его в
`metadata.namespace`, а объект, отрисованный для другого неймспейса, отклоняется до создания.

Входы `release` и `env-bundle-secret` устарели: если они заданы, они должны совпадать с values.

### Владение релизом

Несколько сервисов могут жить в одном неймспейсе (`backend` и `lk-frontend` в `dev-lk-backend`) — у каждого
свой релиз. Чтобы ошибка в values не позволила одному сервису обновить, откатить или заменить релиз другого,
релиз помечается меткой Helm `akjet.kz/source-repository=<владелец>.<репозиторий>`. Перед любым изменением
job деплоя читает записи релиза (ConfigMap'ы Helm) и останавливается, если релиз принадлежит другому
репозиторию. Релиз без метки (установлен прежней версией workflow) получает её при следующем деплое.

### Набор конфигурации окружения (`env-bundle`)

Для сервиса с десятками переменных вызывающий передаёт один секрет — JSON-объект с конфигурацией одного
окружения. Что означает каждый ключ, определяют файлы сервиса, а не workflow; новая переменная не требует
правки workflow.

```yaml
    secrets:
      env-bundle: ${{ secrets.DEV_BACKEND_ENV }}     # {"DEV_DB_PASSWORD": "...", "DEV_DB_HOST": "..."}
```

| | |
|---|---|
| Ключ | `<ОКРУЖЕНИЕ>_<ИМЯ>`: `DEV_` для `dev`. Ключ с другим префиксом — ошибка |
| Значение | строка JSON любого содержания, в том числе многострочная; пустая строка = «не задано» |
| `ИМЯ` объявлено в `requiredSecrets` | ключ Kubernetes Secret'а `<релиз>-<secret>` |
| `ИМЯ` есть в `overrides` файла `overrides.yaml` | заменяет `config.<ИМЯ>`; проверяется как переменная репозитория и применяется поверх неё |
| Любое другое `ИМЯ` | ошибка: значение из values-файла без записи в `overrides` из GitHub не меняется |
| Обязательность | обязателен каждый ключ `requiredSecrets`, кроме перечисленных в `secrets.optional` |
| Где проверяется | job проверки (раннер GitHub): до старта job'а деплоя, без обращения к кластеру |
| Что переходит в job деплоя | только имена (план «ключ Secret'а ← имя в наборе») и несекретные переопределения |
| Запись | как у `app-secrets`: server-side apply через stdin, владение только переданными ключами, перезапуск при изменении |
| Совместно с `app-secrets` | нельзя; при `validate-only` и для `stage` — ошибка запуска |
| Размер | лимит GitHub — 48 КБ на секрет; workflow предупреждает с 44 КБ |

Дополнительные разделы `<values-dir>/overrides.yaml`:

```yaml
secrets:
  aliases:                      # имя в наборе -> <secret>.<КЛЮЧ>, только если имя отличается от ключа
    DB_MIGRATOR_PASSWORD: migrate.DB_PASSWORD
  optional: [app.REDIS_PASSWORD, integrations.*]   # могут отсутствовать
locked:
  dev: [SMS_DRIVER, PAYOUT_DISABLED]               # для этого окружения нельзя задать ни набором, ни переменной
```

Один ключ, объявленный в двух Secret'ах (пароль приложения и пароль миграций), обязан иметь псевдоним:
иначе проверка останавливается.

Оператору: `scripts/env-bundle.sh template <env>` печатает заготовку набора, `scripts/env-bundle.sh check
<env> <файл>` выполняет тот же шаг, что и workflow, и выводит только имена. Скрипт работает с любым
окружением, для которого есть `values-<env>.yaml`; сам workflow по-прежнему знает только `dev` и `stage`.

### Набор без объявления переменных (сквозной режим)

`deployment.envBundle.secret: <имя Secret'а из requiredSecrets>` в values включает сквозной режим набора. Он
нужен сервису, у которого переменных много и они меняются без участия Git.

```yaml
# values.yaml сервиса
deployment:
  envBundle:
    secret: app
# k8s-deploy.yml сервиса
    secrets:
      env-bundle: ${{ secrets.DEV_BACKEND_ENV }}
```

| | Обычный режим | Сквозной режим |
|---|---|---|
| Ключ `<ENV>_<ИМЯ>` | должен быть объявлен в `requiredSecrets` или `overrides` | любой; становится ключом `ИМЯ` указанного Secret'а |
| Проверка значения | по типу для `overrides` | нет; строка, число или логическое значение сохраняются как есть |
| Обязательные ключи | все из `requiredSecrets`, кроме `secrets.optional` | нет |
| `locked.<env>` | действует | на набор не действует (остаётся для переменных репозитория) |
| `secrets.aliases` | действует | действует: псевдоним уводит значение в другой Secret |
| Пустая строка | «не задано» | «не задано», ключ не записывается |

Проверяется в сквозном режиме только форма: набор — объект JSON; ключи начинаются с префикса окружения; имя
после префикса годится как имя переменной окружения; значение не `null`, не объект и не массив; указанный
Secret объявлен в `requiredSecrets`. Некорректный JSON останавливает запуск в job'е проверки, до обращения к
кластеру.

Приоритет над values-файлами. В Deployment'ах чарт подключает `envFrom` в порядке «ConfigMap, затем Secret»,
поэтому ключ Secret'а перекрывает одноимённое значение из `config`; явных `env` у workload'ов нет. У Job'а
миграций конфигурация задана явными `env`, которые сильнее `envFrom`: для него workflow убирает записи с
именами, которые даёт набор. Значения из `migration.config` (роль миграций) не убираются никогда.

Создание и обновление Secret'а в сквозном режиме:

| Ситуация | Что делает workflow |
|---|---|
| Secret'а нет | создаёт его одним запросом сразу с полным содержимым (`kubectl create -f -`, тип `Opaque`) |
| Secret есть | сливает переданные ключи (`kubectl patch --type=merge`); остальные ключи не трогает и не удаляет |
| Содержимое не изменилось | ничего не меняет, перезапуск не запрашивается |
| Другой запуск создал Secret одновременно (`AlreadyExists`) | не ошибка: ключи сливаются в созданный Secret |
| `Forbidden` или недоступный API при чтении | остановка с точной причиной; за «Secret'а нет» не принимается |

Раннеру нужны `get` и `patch` на Secret'ы неймспейса и `create` для первого деплоя; `list` и `delete` не
используются. Все права и состояние Secret'ов проверяются до первой записи. Обычный режим набора и `app-secrets`
не изменились: там Secret должен существовать заранее и не создаётся.

Ключ, убранный из набора, из Secret'а не удаляется — его удаляет оператор отдельно.

Сервису с одним пользователем базы для приложения и миграций достаточно не объявлять отдельный Secret миграций:
Job миграций подключает тот же Secret, что и workload'ы, а его явные `env` с именами из набора убираются.

### Секреты приложения из GitHub

Необязательный секрет `app-secrets` переносит значения из секретов репозитория в ключи Kubernetes Secret'ов,
которые релиз объявил в `requiredSecrets`. Вызывающий составляет его сам, строка на значение:

```yaml
    secrets:
      app-secrets: |
        app.DB_PASSWORD=${{ secrets.DEV_DB_PASSWORD }}
        migrate.DB_PASSWORD?=${{ secrets.DEV_DB_MIGRATOR_PASSWORD }}
```

| | |
|---|---|
| Формат строки | `<secret>.<КЛЮЧ>=<значение>` → ключ `КЛЮЧ` в Secret'е `<релиз>-<secret>` |
| `?=` вместо `=` | значение необязательно: пока секрет репозитория не задан, ключ не трогается |
| Пустое значение без `?` | деплой останавливается до любых изменений; в сообщении — только имя ключа |
| Что можно записать | только пары `<secret>.<КЛЮЧ>`, объявленные в `requiredSecrets` values-файлов окружения |
| Кто получает значения | один шаг job'а деплоя (раннер в кластере); job проверки знает только, передан ли секрет |
| Когда нельзя передавать | при `validate-only` и для `stage` — запуск завершается ошибкой |
| Запись | `kubectl apply --server-side`, значения идут через stdin; workflow владеет только перечисленными ключами, остальные ключи Secret'а не меняются |
| Где значения не появляются | ConfigMap, values, запись релиза Helm, выходы job'ов, артефакты, summary, файлы на раннере, журнал (каждое значение маскируется до первого использования) |
| Перезапуск | если Secret изменился, pod'ы релиза перезапускаются тем же деплоем |
| Ключ убран из списка или его необязательный секрет удалён | при следующем деплое ключ удаляется из Secret'а (workflow владеет только тем, что перечислено сейчас) |
| Ограничение | значение — одна строка; многострочные значения не поддерживаются |

Объект Secret'а workflow не создаёт. Платформа создаёт пустой Secret и выдаёт раннеру `get` и `patch` на
него по имени (`ciManagedSecrets` неймспейса в `k8s-infra`). Без этого шаг останавливается с сообщением,
какого права или объекта не хватает.

Секреты репозитория GitHub не привязаны к ветке: их может прочитать workflow из любой ветки, в которую
у участника есть право записи. Разделение `DEV_*` / `STAGE_*` — соглашение об именах, а не граница доступа.

1. **Проверка** (GitHub-hosted, без доступа к кластеру): входы, наличие файлов values, `helm lint`,
   рендер, `kubeconform -strict`. Допустимы только ConfigMap, ServiceAccount, Deployment, Service и
   Job; явный `metadata.namespace` и образ без digest отклоняются. HTTPRoute релиз приложения не
   создаёт: маршруты принадлежат платформе (компонент gateway-route в k8s-infra), поэтому
   `httpRoute.enabled: true` в values сервиса приводит к ошибке проверки.
2. **Проверка раннера**: job идёт внутри кластера под ServiceAccount'ом pod'а, kubeconfig отсутствует.
3. **Секреты приложения** (если передан `app-secrets`): проверка значений и прав, затем запись.
4. **Миграции** (при `run-migrations`): Job создаётся до обновления; сбой останавливает деплой.
   - Если у релиза есть незавершённый Job миграций (метки `app.kubernetes.io/instance` +
     `app.kubernetes.io/component=migration`, нет условия Complete/Failed/Suspended), второй не создаётся.
   - Job опрашивается каждые 10 с до `deployment.migrationWaitTimeoutSeconds`. Успех — только условие
     `Complete=True` Job'а; `Failed=True` — сбой с причиной. Работающий pod успехом не считается,
     `ContainerCreating` — ожидание (скачивание образа), `ImagePullBackOff` и подобные — предупреждение один
     раз. Раз в минуту печатается строка прогресса (счётчики Job'а, фаза pod'а, состояние контейнера).
   - Временные ошибки API повторяются до 6 раз подряд; Forbidden/Unauthorized и исчезновение Job'а — сбой.
   - При сбое печатаются условия Job'а, состояние pod'а и контейнера, события; лог — только если контейнер
     запускался. Переменные окружения не печатаются.
   - Истекло ожидание, а контейнер не стартовал — Job приостанавливается (`suspend`), не удаляется.
     Контейнер стартовал — Job не трогается (миграция может идти); его остановит Kubernetes по
     `migration.activeDeadlineSeconds`.
   - Проверка values: `migration.activeDeadlineSeconds` (считается от старта Job'а, скачивание образа
     входит) должен заканчиваться минимум за 60 с до конца ожидания, чтобы Job всегда завершался под
     наблюдением; ожидание + rollout + 900 с не должны превышать 7200 с — `timeout-minutes: 120` job'а деплоя.
5. **Обновление**: `helm upgrade --install --rollback-on-failure --wait`, `HELM_DRIVER=configmap`.
6. **Проверка rollout** всех Deployment'ов релиза.
7. **Диагностика при сбое**: история релиза, состояние workload'ов и контейнеров, события. Содержимое
   Secret'ов, спецификации pod'ов и переменные окружения не печатаются.

Одновременно выполняется один деплой на цель (неймспейс + релиз из values); идущий деплой не отменяется.

### Откат

- Неуспешный rollout откатывается автоматически на предыдущую ревизию.
- Плановый откат — деплой предыдущего digest с values того же коммита.
- Схема базы не откатывается никогда.

## Требования к раннеру

Workflow не создаёт раннеры и не содержит учётных данных кластера. Платформа должна предоставить:

| Требование | Значение |
|---|---|
| Метка раннера | `akjet-ds-apps` — один общий scale set ARC для всех репозиториев приложений |
| Регистрация | на уровне организации; на GitHub Free — группа раннеров Default, т. е. доступен любому репозиторию организации |
| Расположение | pod внутри целевого кластера под ServiceAccount'ом `arc-runners/app-deployer`; kubeconfig на раннере нет |
| Инструменты в образе | `bash`, `curl`, `tar`, `sha256sum`, `git`, `base64`; `jq` — если сервис передаёт `env-bundle`. Helm и kubectl workflow ставит сам, с проверкой контрольных сумм |
| Исходящий доступ | API кластера; `github.com`, `ghcr.io`, `get.helm.sh`, `dl.k8s.io` |

## Права деплоя

ServiceAccount общего раннера (`arc-runners/app-deployer`) получает namespaced Role **только в
DEV-неймспейсах приложений, для которых включены workload'ы**; кластерных прав и прав в STAGE у него нет:

| Ресурсы | Права |
|---|---|
| Deployment, ReplicaSet | чтение и изменение |
| Service, ConfigMap, ServiceAccount | чтение и изменение (в ConfigMap хранятся данные релиза Helm) |
| Job | создание и чтение |
| Pod, журнал pod'а, Event | только чтение |
| **Secret** | **нет доступа**, кроме `get` и `patch` на Secret'ы, перечисленные платформой по именам (`ciManagedSecrets`) |

Если раннер может читать, перечислять или создавать любые Secret'ы неймспейса, workflow выводит предупреждение.

Именованный доступ не меняет главного ограничения Kubernetes: тот, кто создаёт Deployment'ы в неймспейсе,
может смонтировать любой его Secret. Новое здесь только право перезаписать перечисленные Secret'ы.

## Ограничения GitHub Free

- В приватных репозиториях на тарифе Free нет Environments, их секретов и защиты веток. Поэтому
  workflow не использует `environment:` и не рассчитывает на согласование деплоя средствами GitHub.
- Общий раннер `akjet-ds-apps` находится в группе Default организации: ограничить группы раннеров
  отдельными репозиториями на тарифе Free нельзя. Любой участник с правом записи в любой репозиторий
  организации может запустить на нём произвольный workflow. Поэтому граница проводится в кластере:
  ServiceAccount раннера имеет только namespaced Role в DEV-неймспейсах включённых приложений, без
  RBAC и сетевых политик, из Secret'ов — только перечисленные платформой по именам, и никакие учётные
  данные других окружений на раннере не лежат.
- Рантайм-секреты приложения можно передать из Repository Secrets только явным перечислением
  (`app-secrets`, раздел выше) и только в DEV. Workflow другого репозитория организации, запущенный на
  общем раннере, может перезаписать те же Secret'ы: для DEV это принятый риск, для STAGE — нет.
- `secrets: inherit` не используется: он передаёт вызываемому workflow все секреты репозитория.

## Что не реализовано

- Деплой в окружения, кроме `dev`; диспетчер STAGE.
- Продвижение одного digest между окружениями.
- Подстановка значений из GitHub Variables: несекретная конфигурация задаётся в values-файлах.
- Подпись происхождения образа.
